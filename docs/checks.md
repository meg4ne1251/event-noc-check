# チェック仕様

この文書は初期実装の検査条件と判定を記載します。OS固有の制約・実装上の補足は末尾を参照してください。

## 共通の実行方針

- 主用途は会場設営時に各所を回って行う開通確認とし、初期版はmacOS・Linuxの両方を対応対象とする。OSバージョン・ディストリビューションごとの確認状況は検証記録を参照する。
- プロファイル未指定時は、本書の診断項目をすべて実行し、結果を画面に表示して終了する。ファイルや保存先ディレクトリは作成しない。
- `--profile <path>` でプロファイルを明示した場合は、指定された検査項目と保存設定を適用する。プロファイルを自動探索・自動読込しない。
- 既定ではIPv4・IPv6の両方を対象とし、各チェックの通信経路を固定する。
- `--ipv4-only` / `--ipv6-only` で明示的に対象を絞れるようにする。両方を同時指定した場合は入力エラーにする。
- 接続先、DNS問い合わせ名、HTTPSのURL、タイムアウト、回数、パケットサイズは変更可能にする。
- 各チェックに期限を設け、すべての試行を含む実行全体にも上限を設ける。
- 小さいパケットでの疎通と大きいパケットでの疎通を比較する。
- チェックに失敗しても、実行できる残りの項目は続行する。
- 通常の接続状態チェックで設定を変更しない。SSIDやMACアドレスの収集は初期仕様に含めない。

## 標準値と時間配分

次はプロファイル未指定時にも使う既定値です。設定で変更でき、適用値を結果に含めます。

| 対象 | 初期値 |
| --- | --- |
| IPv4・IPv6の接続先 | `1.1.1.1`、`2606:4700:4700::1111`。ping・指定DNS・MTU・tracerouteでそれぞれ独立して設定 |
| 接続状態 | 取得期限5秒 |
| ping | 各宛先5回、送信間隔1秒、1回の応答待ち2秒、宛先ごとの期限12秒 |
| 直接DNS | 問い合わせ名 `google.com`。各サーバー・方式・レコード種別について1回2秒、無応答時のみ最大2回（初回を含む）、項目ごとの期限5秒 |
| OSのDNS | 問い合わせ名 `google.com`。A・AAAAそれぞれ期限5秒。再試行はOSに依存するため固定回数とみなさない |
| HTTPS | `https://www.google.com/generate_204`、GET、期待値 `204`・本文なし。各経路の名前解決を含む期限15秒 |
| MTU | サイズ一覧 `[1200, 1280, 1400, 1450, 1480, 1492, 1500]`、各3回。比較用64バイトも3回。送信間隔1秒、応答待ち2秒、各サイズの期限8秒 |
| traceroute | UDP、宛先ポート33434から増加、最大30ホップ、各ホップ3回、応答待ち1秒、各経路の期限60秒 |
| AS情報照会 | 既定で有効。RIPEstat HTTPS API、リクエストごとの期限3秒、再試行なし、全照会で15秒以内 |
| 同時実行・頻度 | 通常の検査ジョブは最大4、tracerouteはIPv4・IPv6各1の最大2。ICMPは宛先ごとに毎秒1回以下、tracerouteは各経路毎秒10プローブ以下 |
| 全体期限 | 診断開始から180秒。設定検証・依存確認の対話時間は含めない |

- 基本検査（接続状態・ping・DNS・HTTPS）、MTU、traceroute、AS情報付加の順に実行する。各段階の上限は35秒・65秒・60秒・15秒とし、段階内では上記の同時実行数で実行する。未選択の段階は実行しない。残り5秒は取消・結果集約などのための余裕とする。
- 各項目・段階・全体の期限のうち、最も早い期限を適用する。早く完了すれば次に進み、上限まで待たない。遅い検査だけで後続項目の実行時間を使い切らないようにする。
- 期限到達時は動作中の処理を取り消し、得られた部分結果・打切り理由を残す。未送信・未実行分は `SKIP` とする。tracerouteの部分結果の扱いは個別仕様に従う。
- これらは運用上の初期設定であり、一般的なネットワーク性能の基準ではない。OSごとの実行引数・頻度制御・取消方法は実装時に検証し、要求条件を実現できない場合は理由を表示する。

## 検査プロファイル

初期形式はJSONとし、設定のスキーマバージョンを `schema_version: 1` で指定する。[JSON Schema](schema/profile.schema.json) と次の規則・標準値を使用する。

| 設定 | 意味・省略時の扱い |
| --- | --- |
| `schema_version` | 必須。未対応バージョンは入力エラー |
| `name` | 任意のプロファイル名。指定時は画面・ログ・JSON結果に含める |
| `checks` | 必須。実行する検査IDの空でない配列。省略による全項目実行はしない |
| `ip_versions` | 対象のIPバージョン。省略時は `[4, 6]`。指定する場合は4・6の空でない配列 |
| `ping.targets` | `icmp` の宛先IPアドレスの配列。省略時は標準のIPv4・IPv6宛先。指定時は既定一覧を置き換える |
| `ping.count` | `icmp` の宛先ごとの送信回数。省略時は `5`。正の整数で指定 |
| `dns.servers` | 直接問い合わせするDNSサーバーのIPアドレスの配列。省略時は標準のIPv4・IPv6サーバー。指定時は既定一覧を置き換える |
| `dns.name` | 指定DNS・OSのDNSで問い合わせる名前。省略時は `google.com` |
| `https.url` | HTTPS接続先。省略時は `https://www.google.com/generate_204` |
| `mtu.packet_sizes` | IPパケット全体のサイズの空でない整数配列。省略時は `[1200, 1280, 1400, 1450, 1480, 1492, 1500]`。指定時は既定一覧を置き換える |
| `traceroute.as_lookup` | 公開ホップIPのAS番号・AS登録組織名を照会するか。省略時は `true` |
| その他の接続先・検査条件 | 各検査の宛先、期待するHTTP応答、タイムアウト、回数、注意閾値などを変更可能にする。キー・上限は末尾の「初期実装の補足と設定上限」を参照 |
| `output.text_log` | テキストログを保存するか。省略時は `false` |
| `output.directory` | 保存先。保存が有効な場合の省略値は `results`。相対パスは実行時の作業ディレクトリを基準にする |

選択可能な検査IDは `connection`、`icmp`、`dns_udp`、`dns_tcp`、`system_dns`、`mtu`、`https`、`traceroute` とする。`dns_udp` と `dns_tcp` は、それぞれ選択した通信経路でA・AAAAの両方を問い合わせる。`system_dns` の実際の通信経路はIPバージョン指定で固定できるとみなさない。

- 読めないファイル、不正なJSON、未知のキー・検査ID、重複した検査ID・IPバージョン、不正な型・値は入力エラーとし、通信を始めず終了コード `2` で終了する。全項目実行へ暗黙に切り替えない。
- 適用順は組み込み既定値、指定プロファイル、明示したCLIオプションの順とする。CLI内で矛盾した指定は入力エラーにする。
- `--packet-size` は繰り返し指定可能とし、指定した一覧で `mtu.packet_sizes` を置き換える。単独の `--packet-size 1500` なら1500バイトだけを検査する。重複サイズは入力エラーとし、実行は小さい順にする。`--no-as-lookup` はAS情報照会を無効にする。
- プロファイル未指定時も、`--ipv4-only` / `--ipv6-only` は対象の通信経路を絞る。検査項目自体は全項目のままとする。
- 未選択の検査項目は対象外として扱い、依存コマンドの不足確認や総合判定に含めない。
- 検査の内部処理と選択項目を区別する。例えば `https` には接続先の名前解決が必要であり、`mtu` には比較用の小さいパケットの疎通確認が必要となる。これらの前提処理は実行するが、未選択の検査一式を暗黙に追加しない。
- 選択項目を実行できなかった場合は、未選択の場合と区別して `SKIP` と理由を記録する。
- `ping.targets` と `dns.servers` は独立して設定する。各配列は空にできず、IPリテラルで指定し、不正なアドレスと同一IPの重複を入力エラーとする。ホスト名の解決による宛先変更は行わない。
- 各一覧から対象IPバージョンのアドレスを選ぶ。対象外のIPバージョンの宛先は送信対象に含めず、対象外と表示する。該当する検査を選択しているのに、選択したIPバージョンの宛先が1件もない場合は入力エラーとし、既定宛先を補わない。
- 宛先数、送信回数、DNS試行回数、同時実行数、送信頻度に上限を設け、上限を超える設定は診断前に入力エラーとする。上限値・送信間隔の詳細は末尾に記載する。
- 実際のプロファイルは `local/` または `*.local.*` に置く。リポジトリ内の設定例にはダミー値を使う。

## 画面表示とテキストログ

- 画面表示は常に行い、既定では人向けの日本語テキストとする。`--format json` は標準出力をJSONにする指定であり、ファイル保存を有効にしない。
- プロファイルの `output.text_log` が `true` の場合だけ、UTF-8のテキストログ（`.log`）を保存する。JSON画面出力との併用時も、保存するログは人向けのテキストとする。
- 保存するログには、実行日時、適用プロファイルと検査条件、各検査の対象・IPバージョン・経過時間・判定・理由、総合判定を含める。取得できない値は理由を添える。
- pingは各宛先の各試行と集計、DNSは各サーバー・通信経路・レコード種別・転送方式ごとの結果を、画面・JSON・有効時のテキストログに含める。「記録」はこれらの診断結果への格納を指し、保存設定のない実行でファイルは作らない。
- 保存先は `results/` または `reports/` 配下を基本とする。保存時だけ必要なディレクトリを作り、実行日時と衝突を防ぐ識別子で実行ごとに別ファイルを作る。既存ファイルを上書きしない。
- 保存先と書込権限は診断前に確認し、準備に失敗したら理由を表示して終了コード `2` で終了する。実行中の書込失敗も明示して終了コード `2` とし、可能な限り残りの診断と画面表示は続ける。
- 入力不正や依存確認で診断前に中断した場合は、診断結果ファイルを作らない。
- `output` の省略時、`text_log: false`、プロファイル未指定時は、ファイル保存も保存先ディレクトリの作成も行わない。
- HTTP応答本文、Cookie、認証ヘッダーは保存しない。ログには会場や端末の情報が含まれ得るため公開しない。

## 依存コマンド不足時の動作

診断前に、選択項目の実行に必要な外部コマンドだけを確認する。`traceroute` などが不足していた場合は、不足一覧、影響する検査、OS・ディストリビューションに合ったインストール方法を表示する。環境を判別できない場合は、一律のインストールコマンドを決め打ちせず、確認すべきツールと導入手順の確認先を案内する。ツールを本CLI内から自動インストールしたり、管理者権限へ自動昇格したりしない。

端末で対話可能な場合は、不足項目をまとめて提示して次の二択を尋ねる。

| 選択 | 動作 |
| --- | --- |
| 続行 | 不足コマンドが必要な項目を `SKIP`（理由: 依存コマンド不足）として記録し、他の検査を実行する。全体成功にしない |
| 中断 | ネットワーク診断を開始せず終了コード `2` で終了する |

- 空入力の既定は中断とし、入力終了（EOF）でも中断する。
- 対話できない場合は入力待ちに入らず、既定で不足理由を表示して終了コード `2` で中断する。
- 自動実行向けに `--on-missing skip` / `--on-missing abort` を用意し、指定時は対話せず選択した方針を適用する。不足がなければそのまま診断する。
- 案内と対話は標準エラー出力を使用し、JSONの標準出力へ混ぜない。診断開始前に中断した場合も、JSONモードでは機械可読な起動エラーを返す。
- 権限不足や未対応の機能は依存コマンド不足と区別し、インストールを勧めて解決した扱いにしない。実行時にコマンドが利用不能になった場合も理由を記録し、他の検査を続ける。

## 診断項目

| 項目 | IPv4 | IPv6 | 記録する情報 |
| --- | --- | --- | --- |
| 接続状態 | アドレス、デフォルトルート | アドレス、デフォルトルート | 対象インターフェース、経路の有無 |
| ICMP Echo | 複数指定可。既定は `1.1.1.1` | 複数指定可。既定は `2606:4700:4700::1111` | 各宛先に既定5回。各試行の結果、送信・応答数、RTT、ロス、エラー |
| DNS UDP | 指定した全IPv4サーバーのUDP/53 | 指定した全IPv6サーバーのUDP/53 | サーバーごとの問い合わせ名、種別、応答コード、応答時間 |
| DNS TCP | 指定した全IPv4サーバーのTCP/53 | 指定した全IPv6サーバーのTCP/53 | サーバーごとの問い合わせ名、種別、応答コード、応答時間 |
| OSのDNS | OSリゾルバーによる名前解決 | OSリゾルバーによる名前解決 | A/AAAAの応答と指定DNSとの差異 |
| 大きなICMPパケット | DFを指定 | 送信元での断片化を禁止 | 要求サイズ、実際の送信条件、応答・エラー |
| HTTPS | IPv4に固定 | IPv6に固定 | TCP接続、TLS検証、HTTPステータス、応答時間 |
| traceroute | IPv4に固定 | IPv6に固定 | 宛先、応答したホップ、各応答時間、宛先到達の有無、実行条件 |

OSのDNS確認では、A/AAAAレコードが得られたことからDNS通信自体のIPv4/IPv6を推定しません。OSリゾルバーの実際の通信経路が取得できない場合は「OS設定経由・通信経路不明」と表示します。

### ICMP Echo（ping）

- `ping.targets` に指定した全宛先を対象にする。プロファイル未指定時や一覧の省略時は、標準のIPv4・IPv6宛先を使用する。対象IPバージョンの選択は共通規則に従う。
- 既定では **各宛先に5回** ICMP Echoを送信する。全宛先を合わせて5回ではない。`ping.count` で変更可能にし、応答の有無にかかわらず通常は設定回数の試行を行う。
- 一部宛先の失敗や無応答で残りの宛先を打ち切らない。一括診断として設定回数で終了し、常時監視は初期仕様に含めない。
- 宛先ごとに、予定回数、実送信数、応答数、ロス率、各試行の番号・RTTまたはタイムアウトなどの理由、応答RTTの最小・平均・最大、検査の経過時間を記録する。RTTを取得できなければ未取得の理由を示し、値を補わない。
- 全体期限や実行不能により5回を完了できなかった場合は、実際の試行数と打切り理由を示す。未送信の試行をパケットロスに数えず、未実行分は `SKIP` として未確認であることを残す。全く送信できなかった宛先のロス率は算出しない。
- ロスは必ず結果に残し、部分的なロスの注意判定は共通の閾値設定に従う。全試行が無応答の場合は原則 `FAIL` とし、同じ通信経路でDNS・HTTPSが成功している場合は共通の判定規則に従い `WARN` とする。別のping宛先の成功だけでは無応答宛先の判定を成功にしない。
- この送信回数・宛先一覧は通常の `icmp` 検査に適用する。大きなパケットとtracerouteはそれぞれの検査条件を使い、複数ping宛先へ暗黙に展開しない。

### DNS

`dns.servers` に指定した全DNSサーバーへ直接問い合わせます。既定は `1.1.1.1` と `2606:4700:4700::1111` です。DNSサーバーへのpingやTCP接続だけで成功とせず、実際のDNSクエリと応答を検証します。

通信経路、レコード種別、転送方式を分けます。両方式を選択し、IPv4・IPv6各1台を対象とした場合は次の8通りとなり、サーバーを追加した場合も各サーバーで同じ検査を行います。

| DNSサーバーへの通信経路 | 問い合わせるレコード | 転送方式 |
| --- | --- | --- |
| IPv4 | A | UDP、TCP |
| IPv4 | AAAA | UDP、TCP |
| IPv6 | A | UDP、TCP |
| IPv6 | AAAA | UDP、TCP |

AAAAの応答が得られてもIPv6通信ができたことにはなりません。IPv6のDNSサーバーへAを問い合わせる場合もあります。

- 各サーバーのIPアドレスに対応する通信経路を固定し、選択した `dns_udp` / `dns_tcp` それぞれでA・AAAAを問い合わせる。両方式を選択した場合はサーバー1台あたり4通りで、pingの送信回数5回はDNSに適用しない。
- あるサーバーの失敗後も残りのサーバーを検査する。「いずれか1台が応答すれば成功」という扱いにはせず、各サーバーの失敗を個別結果と総合判定に残す。
- サーバーIP、通信経路、問い合わせ名、レコード種別、転送方式、試行数、応答コード、取得レコード、応答時間、判定・理由を記録する。異なるサーバーの応答内容が違うだけで直ちに異常とは判定しない。
- 既定の問い合わせ名は `google.com` とし、指定DNSとOSのDNSで共通に使う。A・AAAAの取得を期待し、実装時の明示的な実ネットワーク検証で動作を確認する。応答IPを固定値で比較しない。
- `NOERROR` だけで成功にしない。必要なレコードを得られたかも確認する。
- UDP応答のTCフラグ（切り詰め）を記録する。TCPへの再試行結果はUDPの結果と分ける。
- UDPが失敗しTCPが成功した場合も、UDPの問題を結果に残す。
- タイムアウト、`NXDOMAIN`、`SERVFAIL`、応答の欠落を区別する。
- DNSSEC、EDNSの応答サイズ、DoH/DoTは後続の拡張候補とする。

### 大きなパケット・MTU

`--packet-size` は **IPヘッダーを含むIPパケット全体のバイト数** とします。EthernetやWi-Fiのフレーム全体のサイズではありません。

既定では **1200・1280・1400・1450・1480・1492・1500バイト** を小さい順に各3回検査する。MTU検査の宛先は標準のIPv4・IPv6宛先とし、通常pingの宛先設定とは独立して変更可能にする。小さい64バイトのパケットを各経路3回送って比較し、サイズごとの各試行・集計・断片化条件・理由を画面・JSON・有効時のログに含める。IPv6で1200バイトのIPパケットを送ることは、リンクMTUを1200へ変更することではない。

| IPパケットサイズ | IPv4 ICMPペイロード | IPv6 ICMPペイロード |
| --- | --- | --- |
| 1280バイト | 1252バイト | 1232バイト |
| 1500バイト | 1472バイト | 1452バイト |

上表はIPv4ヘッダー20バイト／IPv6ヘッダー40バイト、ICMPヘッダー8バイトで、IPオプション・拡張ヘッダーを含まない場合の計算です。

IPヘッダーと断片化の扱いは [IPv4仕様（RFC 791）](https://www.rfc-editor.org/rfc/rfc791.html) と [IPv6仕様（RFC 8200）](https://www.rfc-editor.org/rfc/rfc8200.html)、ICMPv6 Echoの形式は [RFC 4443](https://www.rfc-editor.org/rfc/rfc4443.html#section-4.1) を参照します。

- IPv4ではDFを指定し、途中の断片化で大きなパケットが通ったように見えることを防ぐ。
- IPv6ではルーターによる断片化は行われないが、送信元での断片化は起こり得る。利用するOS・コマンドで送信元の断片化も禁止できることを確認する。
- 条件を満たせないOSや権限では `SKIP` と理由を表示し、MTUチェックが成功した扱いにしない。
- 小さいパケットで疎通が得られなければ、大きいパケットの失敗だけからMTU問題とは断定しない。
- あるサイズの失敗後も、残りのサイズを実行する。小さいパケットが失敗していても実行可能なサイズ検査は続け、比較の前提を満たさないことを表示する。
- 各サイズは全3回の応答があれば通過確認を `PASS` とし、一部または全部の無応答は既定で `WARN` とする。必須サイズとして指定された条件の不達は `FAIL` とする。権限不足・断片化制御不可・未実行は `SKIP`、内部エラーは `ERROR` として区別する。
- ローカルインターフェースのMTU制限、ICMPの応答拒否、経路上の制限、タイムアウトを分けて表示する。
- 1500バイトが通らないこと自体は、ネットワーク全体の故障を意味しない。トンネルなどでMTUが小さい環境もある。
- 指定サイズの試験は、そのサイズでの通過確認とする。経路MTUの上限探索やPMTUDブラックホールの確定診断は後続の機能とする。
- 「応答を確認した最大の試験サイズ」は表示できるが、経路MTUそのものとは表示しない。一時的なロスやICMP制限でもサイズごとの結果が不連続になることがある。
- 想定するMTUを運用側が必須条件として指定した場合は、その条件に基づいて判定する。

### HTTPSと利用可否

- IPv4・IPv6の通信経路を固定し、指定URLへのTCP/443、TLS、HTTPの段階を記録する。
- 証明書検証を有効にし、ホスト名とSNIを正しく扱う。
- 既定のURLは `https://www.google.com/generate_204` とし、GETに対する `204 No Content`・本文なしを期待する。AndroidでHTTPS接続確認に使われるURLを初期値として採用する（[Androidの設定変更](https://android.googlesource.com/platform/frameworks/base/+/11ae28f%5E%21/)）。実装時にIPv4・IPv6双方のDNS・証明書・HTTP応答を明示的に検証する。任意のHTTP応答を一律に成功にしない。
- 既定ではリダイレクトを追わず、3xxと転送先を期待外応答として表示する。後から追跡を許可する場合も、回数・接続先を制限し、経路固定と証明書検証を維持する。
- 接続先IP、名前解決・TCP・TLS・HTTP各段階の所要時間、TLSバージョン、取得可能な証明書の有効期限・検証結果を表示する。暗黙のIPv4フォールバックや環境変数由来のプロキシ経由で、IPv6の直接接続が成功した扱いにしない。
- 想定外の応答はキャプティブポータルの可能性を示せるが、原因の確定には追加確認が必要とする。
- 応答本文、Cookie、認証ヘッダーは通常の結果に保存しない。
- HTTPSの失敗にはDNSの失敗が関係する場合があるため、理由と前段の結果を併記する。

### traceroute

- 既定の宛先は標準のIPv4・IPv6宛先とし、変更可能にする。`ping.targets` の変更ではtracerouteの宛先を変更しない。逆引きを抑止し、UDP方式（宛先ポート33434から増加）、最大30ホップ、各ホップ3回、応答待ち1秒、経路ごとに毎秒10プローブ以下、各経路60秒以内を初期値とする。方式の自動変更はせず、指定方式を利用できない場合は理由を表示する。
- macOSとLinuxのコマンド・オプション、IPv6の実行方法、権限、終了コード、出力形式の違いはOS別の処理へ分離する。コマンド名だけで必要な機能を利用可能と判定しない。
- 宛先まで応答が得られた場合は `PASS`。無応答ホップや上限内の未到達は情報を残して `WARN` とし、それだけで利用不可や障害箇所を確定しない。コマンド利用不能は理由に応じて `SKIP`、解析不能などの内部エラーは `ERROR` とする。
- 途中のホップが応答しないことから、その先の通信が止まっていると推定しない。DNS・HTTPSなどの結果と併せて判断する。
- 各ホップで各試行の応答IP・RTT・ICMPエラーを残す。同じホップで異なるIPが応答した場合はすべて表示し、1つのIPや直列の経路にまとめない。無応答は `*`、未実行は打切り理由を表示する。宛先到達後も、それまでの無応答や部分結果を消さない。

### tracerouteのAS情報

- AS情報はtracerouteの補足情報であり、独立した必須検査にはしない。既定で有効にし、`traceroute.as_lookup: false` または `--no-as-lookup` で無効化できる。
- 応答した公開IPについて、[RIPEstat Network Info](https://stat.ripe.net/docs/data-api/api-endpoints/network-info.html) から包含プレフィックスと広告元AS番号を、[AS Overview](https://stat.ripe.net/docs/data-api/api-endpoints/as-overview.html) からAS登録組織名（holder）を取得する。複数のAS番号が返る場合はすべて残す。
- 表示はホップ番号・応答IP・各試行のRTT・AS番号・AS登録組織名とする。画面・JSON・有効時のログに含め、情報源、取得日時、APIから取得可能なら経路データの基準時刻も記録する。不明と未照会・無効化を区別する。
- 広告元ASと登録組織名は、その応答IPについての参考情報とする。実際に通った全ASやBGP AS_PATH、ルーター・回線の所有者を確定しない。無応答・トンネル・IXP・経路分散などのため、観測IPの並びから完全なASパスは復元できない（[ASレベルtracerouteの研究](https://conferences.sigcomm.org/sigcomm/2003/papers/p365-mao.pdf)）。
- 外部へ送信するのは照会対象の公開ホップIP・AS番号だけとし、ローカル端末情報や経路全体を一括送信しない。プライベート、共有アドレス空間、リンクローカル、ULA、文書用などの特別用途アドレスは送信せず「公開AS照会対象外」とする。
- 照会は同時2リクエスト以下・全体で毎秒4リクエスト以下・最大128リクエスト・全照会15秒以内とし、同じIP・AS番号を実行中のメモリーにキャッシュする。ディスクキャッシュや照会失敗時の無限再試行はしない。[RIPEstatの利用条件・制限](https://stat.ripe.net/docs/data-api/ripestat-data-api) をリリース前に再確認する。
- 照会の通信は利用可能なIP経路で行い、実際に使用した経路を照会メタデータへ残す。この照会成功を対象経路のDNS・HTTPS成功には数えない。API停止、期限到達、経路なし、応答なしでは不明と理由を表示し、取得済みのtraceroute結果を維持する。補足情報が不明なだけで総合判定・終了コードを悪化させない。

## 結果の判定

| 判定 | 意味 |
| --- | --- |
| `PASS` | そのチェックの成功条件を満たした |
| `WARN` | 実行できたが注意が必要。例: ICMP無応答だが同一通信経路のHTTPSは成功、任意サイズの通過失敗 |
| `FAIL` | 必須の通信条件を満たさなかった。例: 指定DNSの名前解決失敗、HTTPSの失敗 |
| `SKIP` | 対象外、依存不足、権限不足、未対応などで実行しなかった |
| `ERROR` | 入力不正や内部エラーで信頼できる結果を得られなかった |

既定ではIPv4・IPv6両方を必須対象とし、片系の経路がない場合も結果に残します。片系のみの運用ではプロファイルまたはCLIで対象を明示的に絞ります。対象外の項目は総合判定に含めません。選択された検査は実行完了を必須とし、依存コマンド不足などで `SKIP` になった場合は「未確認」を表示し、全体成功にしません。各検査の成功条件は個別仕様に従い、任意サイズの通過失敗やtracerouteの未到達などは `WARN` とします。

複数宛先を指定した検査は宛先ごとに判定し、成功した宛先で他の宛先の `WARN` / `FAIL` / `ERROR` / 未確認を隠しません。全体期限で未実行となった宛先・DNS問い合わせも `SKIP` として明示し、全件確認済みとはしません。

ping無応答の場合、同じ通信経路でDNS・HTTPSが成功していれば `WARN` として扱います。複数の結果が失敗しても原因をICMPの結果だけから確定しません。

通常pingの注意閾値は設定可能とし、初期値を次のとおりとする。これは会場で目立つ問題を拾うための運用上の初期値であり、実測後に調整する。

| 条件 | 初期判定 |
| --- | --- |
| 応答RTTの平均が300ms以上、または最大が1000ms以上 | `WARN`。該当する数値と閾値を表示 |
| 部分的なパケットロス（0%より大きく100%未満） | `WARN`。既定5回では1回の欠落で20%。少数試行の観測であり、恒常的なロス率とみなさない |
| 実送信分が全て無応答 | 原則 `FAIL`。同じ通信経路でDNS・HTTPSが成功した場合は `WARN` |
| 未送信・未実行、RTT未取得 | ロスや0msに置き換えず、理由と未確認を表示 |

高いRTTや部分的なロスだけで回線故障を断定せず、DNS・HTTPSの実測と併記する。traceroute途中ホップのRTT・無応答率にはこのping閾値を適用しない。途中ホップのICMP応答制限を利用者通信のロスと混同しない。

総合表示では「設定された検査条件を満たしたか」を示し、インターネット全体や無線品質の保証として扱いません。

### 終了コード

| 終了コード | 意味 |
| --- | --- |
| `0` | 対象のチェックを完了し、`WARN` / `FAIL` / `ERROR` および必須項目の `SKIP` がない |
| `1` | チェックを完了したが、`WARN` / `FAIL` または必須項目の `SKIP` がある |
| `2` | 入力不正、起動不可、依存コマンド不足時の中断、ログ保存失敗、内部エラーなどで指定条件の診断・保存を完了できなかった |

複数の状態がある場合は `2`、`1`、`0` の順で優先します。JSONにはスキーマバージョン、実行日時、適用プロファイル、選択された検査項目と対象条件、各項目の判定・理由・経過時間、総合判定を含めます。[結果の共通スキーマ](schema/result.schema.json) を参照してください。

## 初期実装の対象外

大量トラフィックによる帯域測定、負荷試験、ポートスキャン、Wi-Fiのローミング・電波測定、APやルーターの設定変更は初期実装に含めません。必要に応じて後から明示的な機能として検討します。

## 初期実装の補足と設定上限

Go標準ライブラリと外部コマンドを使います。対応コマンドとOS固有の制約は [README](../README.md#対応範囲と制約) を参照してください。macOS IPv6断片化禁止の権限不足は `SKIP`、必要なコマンド機能が不明・未対応の場合も成功扱いにしません。macOSで個人設定 `.digrc` が存在または確認不能の場合も `SKIP`、Linuxは `dig -r` を使用します。

| 設定キー | 既定値 / 許容値 |
| --- | --- |
| 各 `targets` / `dns.servers` | 1〜16件。選択IPバージョンごとに1件以上必要 |
| `ping.count` / `mtu.count` | 5 / 3、上限10 / 5 |
| `ping.wait_seconds` / `mtu.wait_seconds` / `dns.wait_seconds` | 2、1〜5秒 |
| `ping.interval_seconds` / `mtu.interval_seconds` | 1、1〜5秒 |
| `ping.timeout_seconds` / `dns.timeout_seconds` | 12 / 5、上限35 / 15秒 |
| `mtu.timeout_seconds` / `https.timeout_seconds` | 8 / 15、上限15 / 35秒 |
| `dns.attempts` | 2、1〜2回。明示的なタイムアウト時だけ再試行 |
| `ping.warn_average_ms` / `ping.warn_max_ms` | 300 / 1000、正の数 |
| `mtu.targets` / `traceroute.targets` | pingとは独立した既定のIPv4・IPv6宛先 |
| `mtu.packet_sizes` | 1〜16個、各64〜9000バイト、重複不可 |
| `mtu.required_sizes` | 既定は空配列。packet_sizesの部分集合 |
| `https.status` / `https.empty_body` | 204 / true、HTTPステータスは200〜599 |
| `traceroute.max_hops` / `traceroute.probes` | 30 / 3、1〜30 / 1〜3 |
| `traceroute.wait_seconds` / `traceroute.timeout_seconds` | 1 / 60、1〜3 / 1〜60秒 |
| `total_seconds` | 180、1〜180秒 |

段階の期限（35・65・60・15秒）と最大同時実行数（4、tracerouteは2）は固定です。宛先が多い場合、期限内に収まらない項目は明示的に `SKIP` になります。MTUは同一宛先のサイズを直列実行し、各サイズの間も送信間隔を空けます。通常pingとMTUは単一プローブのコマンドを繰り返し、応答待ち期限でSIGINTを送り実送信数の集計を回収します。取消後200msで終了しなければ強制終了します。送信数が解析できなければ不明とし、ロスを捏造せず `SKIP` にします。

tracerouteはTTL・試行ごとに単一プローブを送信し、宛先ポート引数を33434から増加させます。送信開始の間隔は100ms以上です。各試行のコマンド終了には応答待ちに加えて500msの余裕を与え、経路・段階・全体の期限を優先します。複数フローでの独立した観測であり、BGPパスや同一フローの経路を示しません。

DNSはBIND digを使い、UDPは `+ignore +notcp`、TCPは `+tcp` です。EDNSは無効で、UDPのTC応答は成功扱いにしません。OS DNSはGoのOS設定に従うリゾルバーを利用し、A/AAAAとも調べます。IPバージョンのCLI指定でOS DNSの通信経路を固定したとはみなしません。HTTPSも名前解決自体の通信経路はOS設定に従いますが、接続先へのTCP経路は `tcp4` / `tcp6` に固定します。

AS照会は直列で開始間隔250ms以上、最大128回・15秒・各3秒です。APIのエラー本文は保存しません。特殊用途IPv4およびIPv6の2000::/3外、2001::/23・2001:db8::/32・2002::/16・3fff::/20等は照会対象外です。将来の特殊用途アドレス追加に応じてフィルターを更新します。[RIPEstat利用規則](https://stat.ripe.net/docs/data-api/ripestat-data-api) は2026-10-16に確認（同時8以下、継続的な1日1000回超の利用は登録を案内）。

プロファイルは64KiB以下で、重複キーとnullも拒否します。宛先はmulticast・unspecified・IPv4-mapped IPv6・zone付きIPを許可しません。URLはhttps限定でuserinfo・query・fragmentを許可しません。未知の引数・位置引数は入力エラーです。

### 結果データ

共通結果は `check`、`target`、`ip_version`、`status`、`reason`、`elapsed_ms` と検査別の `details` を持ちます。`ip_version: 0` はOS DNSの通信経路不明です。対象外IPの宛先は適用設定には残しますが結果には生成せず、未実行 `SKIP` と区別します。JSONとテキストに同じ詳細情報を出力します。テキストの詳細欄は構造を保つため整形したJSONです。

- ICMP/MTU: `probes` に番号、判定、理由、送信確認、RTTを記録。`confirmed_sent`、`unknown_sent`、`received`、`loss_percent`、`min_ms`、`average_ms`、`max_ms` で集計。不明値はnull。`time<...` 出力は `rtt_upper_bound: true` で上限値として区別し、集計にもその上限を使います。MTUにはIP全体サイズ、ペイロード、断片化条件、64バイト比較結果を含めます。
- DNS: 問い合わせ名、A/AAAA、転送方式、試行数、rcode、TC、取得レコード。CNAMEを経由する場合は応答セクション内で名前を辿り、無関係な追加レコードを成功に数えません。
- HTTPS: 接続先、DNS/TCP/TLS/HTTP待ち時間、証明書検証、期限、TLSバージョン、ステータス、本文の有無、失敗段階。本文・Cookie・認証ヘッダーを保存しません。HTTP時間は接続取得から最初の応答バイトまでで、未計測はnullです。
- traceroute: TTLごとの全試行、応答IP、RTT、ICMP注記、未実行理由。ASは取得済み、不明、無効、対象外、期限により未照会を区別し、出典・取得時刻・API基準時刻・照会経路を含めます。
- 接続状態: 稼働中でループバック以外のインターフェースのアドレス・MTU、デフォルトルートの有無・インターフェース。MACとSSIDは取得しません。

保存有効時は診断前に保存先と排他的なログファイルを用意し、診断後に書込・同期・クローズのエラーを確認します。新規ディレクトリは0700、ログは0600で作成します。既存ディレクトリの権限は変更しません。外部から強制終了された場合は空・途中のログが残る場合があります。
