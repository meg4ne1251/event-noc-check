# チェック仕様（設計案）

この文書は実装前の要件を整理するものです。記載したCLI、判定、終了コードはまだ実装されていません。

## 共通の実行方針

- 既定ではIPv4・IPv6の両方を対象とし、各チェックの通信経路を固定する。
- `--ipv4-only` / `--ipv6-only` で明示的に対象を絞れるようにする。両方を同時指定した場合は入力エラーにする。
- 接続先、DNS問い合わせ名、HTTPSのURL、タイムアウト、回数、パケットサイズは変更可能にする。
- 各チェックに期限を設け、すべての試行を含む実行全体にも上限を設ける。
- 小さいパケットでの疎通と大きいパケットでの疎通を比較する。
- チェックに失敗しても、実行できる残りの項目は続行する。
- 通常の接続状態チェックで設定を変更しない。SSIDやMACアドレスの収集は初期仕様に含めない。

## 診断項目

| 項目 | IPv4 | IPv6 | 記録する情報 |
| --- | --- | --- | --- |
| 接続状態 | アドレス、デフォルトルート | アドレス、デフォルトルート | 対象インターフェース、経路の有無 |
| ICMP Echo | `1.1.1.1` | `2606:4700:4700::1111` | 応答数、RTT、ロス、エラー |
| DNS UDP | 上記IPv4宛先のUDP/53 | 上記IPv6宛先のUDP/53 | 問い合わせ名、種別、応答コード、応答時間 |
| DNS TCP | 上記IPv4宛先のTCP/53 | 上記IPv6宛先のTCP/53 | 問い合わせ名、種別、応答コード、応答時間 |
| OSのDNS | OSリゾルバーによる名前解決 | OSリゾルバーによる名前解決 | A/AAAAの応答と指定DNSとの差異 |
| 大きなICMPパケット | DFを指定 | 送信元での断片化を禁止 | 要求サイズ、実際の送信条件、応答・エラー |
| HTTPS | IPv4に固定 | IPv6に固定 | TCP接続、TLS検証、HTTPステータス、応答時間 |

OSのDNS確認では、A/AAAAレコードが得られたことからDNS通信自体のIPv4/IPv6を推定しません。OSリゾルバーの実際の通信経路が取得できない場合は「OS設定経由・通信経路不明」と表示します。

### DNS

通信経路、レコード種別、転送方式を分け、次の8通りを直接問い合わせの対象にします。

| DNSサーバーへの通信経路 | 問い合わせるレコード | 転送方式 |
| --- | --- | --- |
| IPv4 | A | UDP、TCP |
| IPv4 | AAAA | UDP、TCP |
| IPv6 | A | UDP、TCP |
| IPv6 | AAAA | UDP、TCP |

AAAAの応答が得られてもIPv6通信ができたことにはなりません。IPv6のDNSサーバーへAを問い合わせる場合もあります。

- 問い合わせ名には、A・AAAAの両方が期待できる公開ドメインを選び、実装時に動作を確認する。現時点では既定名を未決定とする。
- `NOERROR` だけで成功にしない。必要なレコードを得られたかも確認する。
- UDP応答のTCフラグ（切り詰め）を記録する。TCPへの再試行結果はUDPの結果と分ける。
- UDPが失敗しTCPが成功した場合も、UDPの問題を結果に残す。
- タイムアウト、`NXDOMAIN`、`SERVFAIL`、応答の欠落を区別する。
- DNSSEC、EDNSの応答サイズ、DoH/DoTは後続の拡張候補とする。

### 大きなパケット・MTU

`--packet-size` は **IPヘッダーを含むIPパケット全体のバイト数** とします。EthernetやWi-Fiのフレーム全体のサイズではありません。

| IPパケットサイズ | IPv4 ICMPペイロード | IPv6 ICMPペイロード |
| --- | --- | --- |
| 1280バイト | 1252バイト | 1232バイト |
| 1500バイト | 1472バイト | 1452バイト |

上表はIPv4ヘッダー20バイト／IPv6ヘッダー40バイト、ICMPヘッダー8バイトで、IPオプション・拡張ヘッダーを含まない場合の計算です。

IPヘッダーと断片化の扱いは [IPv4仕様（RFC 791）](https://www.rfc-editor.org/rfc/rfc791.html) と [IPv6仕様（RFC 8200）](https://www.rfc-editor.org/rfc/rfc8200.html)、ICMPv6 Echoの形式は [RFC 4443](https://www.rfc-editor.org/rfc/rfc4443.html#section-4.1) を参照します。

- IPv4ではDFを指定し、途中の断片化で大きなパケットが通ったように見えることを防ぐ。
- IPv6ではルーターによる断片化は行われないが、送信元での断片化は起こり得る。利用するOS・コマンドで送信元の断片化も禁止できることを確認する。
- 条件を満たせないOSや権限では `SKIP` と理由を表示し、MTUチェックが成功した扱いにしない。
- 小さいパケットで疎通が得られなければ、大きいパケットの失敗だけからMTU問題とは断定しない。
- ローカルインターフェースのMTU制限、ICMPの応答拒否、経路上の制限、タイムアウトを分けて表示する。
- 1500バイトが通らないこと自体は、ネットワーク全体の故障を意味しない。トンネルなどでMTUが小さい環境もある。
- 指定サイズの試験は、そのサイズでの通過確認とする。経路MTUの上限探索やPMTUDブラックホールの確定診断は後続の機能とする。
- 想定するMTUを運用側が必須条件として指定した場合は、その条件に基づいて判定する。

### HTTPSと利用可否

- IPv4・IPv6の通信経路を固定し、指定URLへのTCP/443、TLS、HTTPの段階を記録する。
- 証明書検証を有効にし、ホスト名とSNIを正しく扱う。
- 宛先のURLと期待するHTTPステータス・応答は実装時に決める。任意のHTTP応答を一律に成功にしない。
- リダイレクトは検出して表示し、回数と接続先に制限を設ける。
- 想定外の応答はキャプティブポータルの可能性を示せるが、原因の確定には追加確認が必要とする。
- 応答本文、Cookie、認証ヘッダーは通常の結果に保存しない。
- HTTPSの失敗にはDNSの失敗が関係する場合があるため、理由と前段の結果を併記する。

## 結果の判定

| 判定 | 意味 |
| --- | --- |
| `PASS` | そのチェックの成功条件を満たした |
| `WARN` | 実行できたが注意が必要。例: ICMP無応答だが同一通信経路のHTTPSは成功、任意サイズの通過失敗 |
| `FAIL` | 必須の通信条件を満たさなかった。例: 指定DNSの名前解決失敗、HTTPSの失敗 |
| `SKIP` | 対象外、依存不足、権限不足、未対応などで実行しなかった |
| `ERROR` | 入力不正や内部エラーで信頼できる結果を得られなかった |

既定ではIPv4・IPv6両方を必須対象とし、片系の経路がない場合も結果に残します。片系のみの運用ではCLIで対象を明示的に絞ります。対象外の項目は総合判定に含めません。選択された必須項目が `SKIP` になった場合は「未確認」を表示し、全体成功にしません。

ping無応答の場合、同じ通信経路でDNS・HTTPSが成功していれば `WARN` として扱います。複数の結果が失敗しても原因をICMPの結果だけから確定しません。RTT・ロスの注意閾値は設定可能とし、既定値は実測後に決めます。

総合表示では「設定された検査条件を満たしたか」を示し、インターネット全体や無線品質の保証として扱いません。

### 終了コード案

| 終了コード | 意味 |
| --- | --- |
| `0` | 対象のチェックを完了し、`WARN` / `FAIL` / `ERROR` および必須項目の `SKIP` がない |
| `1` | チェックを完了したが、`WARN` / `FAIL` または必須項目の `SKIP` がある |
| `2` | 入力不正、起動不可、内部エラーなどで信頼できる診断を完了できなかった |

複数の状態がある場合は `2`、`1`、`0` の順で優先します。JSONにはスキーマバージョン、実行日時、対象条件、各項目の判定・理由・経過時間、総合判定を含めます。詳細なJSONスキーマは実装時に定義します。

## 初期実装の対象外

大量トラフィックによる帯域測定、負荷試験、ポートスキャン、Wi-Fiのローミング・電波測定、APやルーターの設定変更は初期実装に含めません。必要に応じて後から明示的な機能として検討します。
