# event-noc-check（名称案）

イベント会場でWi-Fiを敷設・運用するNOC（Network Operations Center）のためのネットワーク診断CLIプロジェクトです。

コマンドを1つ実行すると、接続したネットワークからインターネットを利用できるかをIPv4・IPv6ごとに確認し、問題がある箇所を切り分けられるツールを目指します。主用途は、会場設営時に各所を回って行う開通確認です。会場ごとの検査プロファイルで確認条件を揃え、必要な場合だけ結果を保存します。

**現在は仕様整理の段階です。実行可能なCLIはまだありません。** リポジトリ名は `event-noc-check`、コマンド名は `noc-check` を提案しています。

## 確認したいこと

| 項目 | 確認内容 |
| --- | --- |
| 接続状態 | インターフェース、IPアドレス、デフォルトルートの有無 |
| IPv4 ping | 複数のIPv4宛先に各5回送信し、宛先ごとの応答・遅延・パケットロスを確認。既定は `1.1.1.1` |
| IPv6 ping | 複数のIPv6宛先に各5回送信し、宛先ごとの応答・遅延・パケットロスを確認。既定は `2606:4700:4700::1111` |
| DNS | 指定した全DNSサーバーへ直接問い合わせ、サーバーごとにA・AAAAレコードを確認。既定は上記のIPv4・IPv6サーバー |
| DNSの転送方式 | UDP/53・TCP/53の両方で名前解決を確認 |
| 大きなパケット | IPv4のDF指定とIPv6の送信元での断片化を禁止する方法で、指定サイズの疎通を確認 |
| Web利用 | IPv4・IPv6それぞれでTCP/443、TLS証明書検証、HTTPS応答を確認 |
| 利用者のDNS | OSに設定されたDNSによる名前解決を、指定DNSへの直接問い合わせと比較 |
| 経路調査 | IPv4・IPv6それぞれのtracerouteで応答したホップと宛先への到達状況を確認 |

CloudflareのIPv6宛先は [公式IPアドレス一覧](https://developers.cloudflare.com/1.1.1.1/ip-addresses/) に基づいています。`1.1.1.1` 自体はIPv4アドレスのため、IPv6の確認には対応するIPv6アドレスを使用します。

pingが成功しただけで「ネットが正常」とは判定しません。DNS・HTTPS・パケットサイズなどの結果を合わせて確認します。また、無線品質、会場全体の収容能力、すべての外部サービスの利用可否を1台の診断で保証するものではありません。

## 想定する使い方（未実装）

以下はCLIの設計案です。現時点では実行できません。

```sh
# 全検査項目をIPv4・IPv6で実行（画面表示のみ、ファイル保存なし）
noc-check

# 会場ごとのプロファイルで検査項目とログ保存の有無を指定
noc-check --profile local/setup.json

# 片方の通信経路だけをチェック
noc-check --ipv4-only
noc-check --ipv6-only

# 大きなパケットの通過確認（IPパケット全体のサイズ）
noc-check --packet-size 1500

# 運用記録・他ツール連携向けのJSON出力
noc-check --format json
```

- プロファイルを指定しなければ全検査項目を実行する。既定ではIPv4・IPv6の両方をチェックし、片方の成功で他方の失敗を隠さない。
- プロファイルは明示的に指定したファイルだけを読み込み、会場設定を自動適用しない。
- 接続先、DNSの問い合わせ名、タイムアウト、回数は設定で変更できるようにする。
- pingの既定送信回数は宛先ごとに5回とし、各回の結果と宛先ごとの集計を表示する。DNSは指定した全サーバーへ問い合わせ、1台の成功で他の失敗を隠さない。
- すべてのチェックに期限を設け、失敗しても残りのチェックを続ける。
- 結果は `PASS` / `WARN` / `FAIL` / `SKIP` / `ERROR` で表示し、理由を添える。
- 画面への表示を基本とし、プロファイルでテキストログ保存を有効にした場合だけファイルを作る。保存設定の省略時やプロファイル未指定時には、ログも結果ディレクトリも作らない。
- `--format json` は画面出力（標準出力）の形式を変更する。指定するだけではファイルを保存しない。

## 会場ごとの検査プロファイル（未実装）

初期のプロファイル形式はJSONとし、検査項目、IPバージョン、複数のping宛先・DNSサーバー、タイムアウトなどの条件、テキストログ保存の有無を指定できるようにします。次はダミーの設定例です。文書用IPのため、実際の診断では接続先を置き換えます。

```json
{
  "schema_version": 1,
  "name": "setup-example",
  "checks": ["connection", "icmp", "dns_udp", "dns_tcp", "system_dns", "mtu", "https", "traceroute"],
  "ip_versions": [4, 6],
  "ping": {
    "targets": ["192.0.2.1", "192.0.2.2", "2001:db8::1", "2001:db8::2"],
    "count": 5
  },
  "dns": {
    "servers": ["192.0.2.53", "192.0.2.54", "2001:db8::53", "2001:db8::54"]
  },
  "output": {
    "text_log": true,
    "directory": "results"
  }
}
```

- `checks` に列挙した項目だけを実行する。未選択の項目は総合判定に含めない。
- `ping.targets` と `dns.servers` は独立した一覧とし、指定時はそれぞれの既定一覧を置き換える。pingの設定は検査ID `icmp` に対応する。
- `ping.count` を省略した場合も、各宛先に5回送信する。送信・応答数、ロス率、各回のRTTまたは失敗理由、RTTの最小・平均・最大を結果に含める。
- DNSは各サーバーについて、選択したUDP・TCP方式でA・AAAAを問い合わせる。DNSサーバーへのpingだけでDNS成功とはしない。
- 結果は宛先別・DNSサーバー別に表示し、ログ保存が有効なら各結果もログに残す。複数宛先の確認は有限回で終了し、常時監視は行わない。
- `output` を省略するか `text_log` を `false` にすると画面表示だけで終了する。
- 保存する場合も画面に結果を表示し、実行ごとに別のUTF-8テキストファイル（`.log`）を作る。`directory` の相対パスはコマンド実行時の作業ディレクトリを基準にする。
- 実際の会場設定は `local/` または `*.local.*` に、結果は `results/` または `reports/` に置き、公開しない。

判定、終了コード、プロファイルの検証規則、DNSとパケットサイズの扱いは [チェック仕様](docs/checks.md) を参照してください。

## 対応OSと依存コマンド（未実装）

初期版の対応対象は **macOSとLinuxの両方** とします。OSごとの外部コマンド、引数、権限、出力の違いを分離して実装します。対応するOSバージョンとLinuxディストリビューションは、実装・動作確認時に明記します。

選択した検査に必要な `traceroute` などのコマンドがない場合は、診断前に不足一覧と環境に合ったインストール方法を案内し、対話式で次の動作を選べるようにします。

- **続行**: 不足コマンドを使う項目を `SKIP` として、実行可能な残りの検査を行う。全体成功にはしない。
- **中断**: 検査を始めず終了する。

自動インストールや管理者権限への自動昇格は行いません。対話できない環境では既定で中断し、`--on-missing skip` を明示した場合は不足項目をスキップして続行する設計です。対話メッセージは標準エラー出力に送り、JSON出力に混ぜません。

## 開発の順序

1. macOS・Linuxの両対応を前提に、実装言語、配布方法、各OSの対応範囲を決める。
2. プロファイル読込、検査項目の選択、依存コマンド確認と対話処理を実装する。
3. IPv4・IPv6のping、DNS、大きなパケット、HTTPS、接続状態、tracerouteを実装する。
4. 一括実行、判定、終了コード、JSON出力、任意のテキストログ保存を整える。
5. 会場ネットワークで検証し、運用手順とリリース方法を整える。

実装言語、配布方法、依存ツールの詳細、ライセンスは未決定です。macOS・Linuxは対応対象として決定しましたが、現時点ではどちらも未実装・未検証です。実装が始まった段階で、インストール方法と実際に動作確認した環境を追記します。

## 公開リポジトリとしての運用

会場固有のSSID、パスワード、内部ネットワーク構成、端末情報、実測ログ、パケットキャプチャ、認証情報はコミットしません。サンプルにはダミー値を使用します。

[.gitignore](.gitignore) でローカル設定・秘密情報・診断結果を除外しています。ただし、除外設定は既に追跡されているファイルや文書内に貼り付けた情報には適用されません。公開前に差分を確認してください。

名称と公開先を決めた後、GitHub CLIを利用する場合は次の手順で公開できます。`<owner>` は自分のアカウントまたは公開先Organizationに置き換えてください。

```sh
git status --short
git diff --cached
# 初回コミットがない場合は、確認した公開用ファイルを追加してコミットする
# GitHub CLIでログイン済みであることを確認したうえで実行
gh repo create <owner>/event-noc-check --public --source=. --remote=origin --push
```

現在の公開・リモート設定状況は `git remote -v` で確認できます。
