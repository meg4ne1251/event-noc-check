# event-noc-check

イベント会場でWi-Fiを敷設・運用するNOC（Network Operations Center）のためのネットワーク診断CLIプロジェクトです。

コマンドを1つ実行すると、接続したネットワークからインターネットを利用できるかをIPv4・IPv6ごとに確認し、問題がある箇所を切り分けられるツールを目指します。主用途は、会場設営時に各所を回って行う開通確認です。会場ごとの検査プロファイルで確認条件を揃え、必要な場合だけ結果を保存します。

**Go製CLI `noc-check` の初期実装があります。** macOS・Linux向けに、8種類の診断、プロファイル、JSON出力、任意のテキストログ保存を実装しています。対応範囲と制約は下記を参照してください。

## 確認したいこと

| 項目 | 確認内容 |
| --- | --- |
| 接続状態 | インターフェース、IPアドレス、デフォルトルートの有無 |
| IPv4 ping | 複数のIPv4宛先に各5回送信し、宛先ごとの応答・遅延・パケットロスを確認。既定は `1.1.1.1` |
| IPv6 ping | 複数のIPv6宛先に各5回送信し、宛先ごとの応答・遅延・パケットロスを確認。既定は `2606:4700:4700::1111` |
| DNS | 指定した全DNSサーバーへ直接問い合わせ、サーバーごとにA・AAAAレコードを確認。既定は上記のIPv4・IPv6サーバー |
| DNSの転送方式 | UDP/53・TCP/53の両方で名前解決を確認 |
| 大きなパケット | IPv4のDF指定とIPv6の送信元での断片化を禁止する方法で、指定サイズの疎通を確認 |
| Web利用 | IPv4・IPv6それぞれでTCP/443、TLS証明書検証、HTTPS応答を確認 |
| 利用者のDNS | OSに設定されたDNSによる名前解決を、指定DNSへの直接問い合わせと比較 |
| 経路調査 | IPv4・IPv6それぞれのtracerouteで応答したホップと宛先への到達状況を確認 |

CloudflareのIPv6宛先は [公式IPアドレス一覧](https://developers.cloudflare.com/1.1.1.1/ip-addresses/) に基づいています。`1.1.1.1` 自体はIPv4アドレスのため、IPv6の確認には対応するIPv6アドレスを使用します。

pingが成功しただけで「ネットが正常」とは判定しません。DNS・HTTPS・パケットサイズなどの結果を合わせて確認します。また、無線品質、会場全体の収容能力、すべての外部サービスの利用可否を1台の診断で保証するものではありません。

## 標準の検査条件

プロファイル未指定時は全検査をIPv4・IPv6で実行し、次の初期値を使います。値はプロファイルなどで変更可能にします。時間・注意閾値は運用上の初期値であり、実装後の検証で調整します。

| 項目 | 初期値 |
| --- | --- |
| ping・指定DNS・MTU・tracerouteの接続先 | IPv4 `1.1.1.1`、IPv6 `2606:4700:4700::1111`。各検査の接続先設定は独立 |
| ping | 各宛先5回、送信間隔1秒、応答待ち2秒 |
| DNS問い合わせ名 | `google.com`。指定DNSとOSのDNSでA・AAAAを確認 |
| 指定DNSへの問い合わせ | UDP・TCPそれぞれ、1回2秒、無応答時のみ最大2回の試行 |
| HTTPS | `https://www.google.com/generate_204` へGET。期待する応答は `204`・本文なし。IPv4・IPv6を固定し、各15秒以内 |
| 大きなパケット | IPパケット全体で **1200・1280・1400・1450・1480・1492・1500バイト**。各サイズ3回、小さい64バイトのパケット3回と比較 |
| traceroute | UDP方式、最大30ホップ、各ホップ3回、応答待ち1秒、各経路60秒以内。逆引きなし |
| AS情報 | tracerouteの応答IPに、公開経路情報からAS番号・AS登録組織名を付加。既定で有効、無効化可能 |
| 注意判定 | pingの平均RTTが300ms以上、最大RTTが1000ms以上、または部分的なロスがあれば `WARN` |
| 診断全体 | 最大180秒。依存確認の対話時間は含めない。終了時は未実行分を明示 |

AS情報はRIPEstatのHTTPS APIで取得する実装です。照会する公開ホップIPは外部サービスに送信されますが、プライベートIPなどは送信しません。取得できない情報は不明として残し、AS情報の照会失敗だけで通信障害とは判定しません。表示するのは「応答IPに対応するASの参考情報」であり、完全なBGP ASパスや各ルーターの所有者を保証するものではありません。

既定では画面表示だけで終了し、ログファイルは作りません。時間配分、サイズ別の結果、AS情報の出典・限界は [チェック仕様](docs/checks.md) を参照してください。

## 使い方

ビルドした `bin/noc-check` を使用します。PATHへ配置した場合は以下のコマンド名で実行できます。

```sh
# 全検査項目をIPv4・IPv6で実行（画面表示のみ、ファイル保存なし）
noc-check

# 会場ごとのプロファイルで検査項目とログ保存の有無を指定
noc-check --profile local/setup.json

# 片方の通信経路だけをチェック
noc-check --ipv4-only
noc-check --ipv6-only

# 大きなパケットの通過確認（IPパケット全体のサイズ）
noc-check --packet-size 1500

# 複数サイズを指定（既定のサイズ一覧を置き換える）
noc-check --packet-size 1200 --packet-size 1400 --packet-size 1500

# tracerouteのAS情報照会を無効にする
noc-check --no-as-lookup

# 運用記録・他ツール連携向けのJSON出力
noc-check --format json
```

- プロファイルを指定しなければ全検査項目を実行する。既定ではIPv4・IPv6の両方をチェックし、片方の成功で他方の失敗を隠さない。
- プロファイルは明示的に指定したファイルだけを読み込み、会場設定を自動適用しない。
- 接続先、DNSの問い合わせ名、タイムアウト、回数は設定で変更できる。
- pingの既定送信回数は宛先ごとに5回とし、各回の結果と宛先ごとの集計を表示する。DNSは指定した全サーバーへ問い合わせ、1台の成功で他の失敗を隠さない。
- すべてのチェックに期限を設け、失敗しても残りのチェックを続ける。
- 結果は `PASS` / `WARN` / `FAIL` / `SKIP` / `ERROR` で表示し、理由を添える。
- 画面への表示を基本とし、プロファイルでテキストログ保存を有効にした場合だけファイルを作る。保存設定の省略時やプロファイル未指定時には、ログも結果ディレクトリも作らない。
- `--format json` は画面出力（標準出力）の形式を変更する。指定するだけではファイルを保存しない。

## 会場ごとの検査プロファイル

初期のプロファイル形式はJSONとし、検査項目、IPバージョン、複数のping宛先・DNSサーバー、タイムアウトなどの条件、テキストログ保存の有無を指定できます。次はダミーの設定例です。文書用IPのため、実際の診断では接続先を置き換えます。

```json
{
  "schema_version": 1,
  "name": "setup-example",
  "checks": ["connection", "icmp", "dns_udp", "dns_tcp", "system_dns", "mtu", "https", "traceroute"],
  "ip_versions": [4, 6],
  "ping": {
    "targets": ["192.0.2.1", "192.0.2.2", "2001:db8::1", "2001:db8::2"],
    "count": 5
  },
  "dns": {
    "servers": ["192.0.2.53", "192.0.2.54", "2001:db8::53", "2001:db8::54"],
    "name": "google.com"
  },
  "mtu": {
    "packet_sizes": [1200, 1280, 1400, 1450, 1480, 1492, 1500]
  },
  "output": {
    "text_log": true,
    "directory": "results"
  }
}
```

- `checks` に列挙した項目だけを実行する。未選択の項目は総合判定に含めない。
- `ping.targets` と `dns.servers` は独立した一覧とし、指定時はそれぞれの既定一覧を置き換える。pingの設定は検査ID `icmp` に対応する。
- `ping.count` を省略した場合も、各宛先に5回送信する。送信・応答数、ロス率、各回のRTTまたは失敗理由、RTTの最小・平均・最大を結果に含める。
- DNSは各サーバーについて、選択したUDP・TCP方式でA・AAAAを問い合わせる。DNSサーバーへのpingだけでDNS成功とはしない。
- 結果は宛先別・DNSサーバー別に表示し、ログ保存が有効なら各結果もログに残す。複数宛先の確認は有限回で終了し、常時監視は行わない。
- `output` を省略するか `text_log` を `false` にすると画面表示だけで終了する。
- 保存する場合も画面に結果を表示し、実行ごとに別のUTF-8テキストファイル（`.log`）を作る。`directory` の相対パスはコマンド実行時の作業ディレクトリを基準にする。
- 実際の会場設定は `local/` または `*.local.*` に、結果は `results/` または `reports/` に置き、公開しない。

判定、終了コード、プロファイルの検証規則、DNSとパケットサイズの扱いは [チェック仕様](docs/checks.md) を参照してください。

## 対応OSと依存コマンド

初期版の対応対象は **macOSとLinuxの両方** とします。OSごとの外部コマンド、引数、権限、出力の違いを分離して実装します。対応するOSバージョンとLinuxディストリビューションは、実装・動作確認時に明記します。

選択した検査に必要な `traceroute` などのコマンドがない場合は、診断前に不足一覧と環境に合ったインストール方法を案内し、対話式で次の動作を選べるようにします。

- **続行**: 不足コマンドを使う項目を `SKIP` として、実行可能な残りの検査を行う。全体成功にはしない。
- **中断**: 検査を始めず終了する。

自動インストールや管理者権限への自動昇格は行いません。対話できない環境では既定で中断し、`--on-missing skip` を明示した場合は不足項目をスキップして続行する実装です。対話メッセージは標準エラー出力に送り、JSON出力に混ぜません。

## 開発・検証

Go 1.23以上を使用します（CIはGo 1.26系）。Goの外部モジュール依存はありません。

```sh
go build -o bin/noc-check ./cmd/noc-check
bin/noc-check --help
go test -race -cover ./...
go vet ./...
# 任意: 公開インターネットへ送信しない、実OSコマンドのループバック試験
NOC_CHECK_LOCAL_COMMANDS=1 go test ./internal/check -run TestLocalOSCommands -v
# 任意: 標準の公開宛先へ実通信（最大180秒）
bin/noc-check --on-missing skip
```

自動テストは疑似コマンド、ローカルHTTP/TLSサーバー、ダミーのDNS応答を使用し、公開DNSなどに依存しません。GitHub ActionsでUbuntuとmacOSのビルド・race検査・ループバック試験を実行します。詳細は [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。

### 対応範囲と制約

- macOSでは標準の `ping` / `ping6`、`route`、`dig`、`traceroute` / `traceroute6` を使用します。
- Linuxではiputilsの `ping`、iproute2の `ip`、BINDの `dig`、Linux traceroute（`-M default -N 1` 対応）を使用します。BusyBox版は対応を保証せず、必要機能がない場合は `SKIP` です。
- macOSのIPv6 MTU検査は `ping6 -D -m` で送信元断片化を禁止します。OSが権限を要求した場合は `SKIP` とし、自動昇格しません。
- macOS標準digには個人設定を無視するオプションがないため、`~/.digrc` が存在または確認不能なら直接DNS検査は `SKIP` です。Linuxでは `dig -r` で個人設定を読みません。EDNSと暗黙のUDP→TCP再試行は使用しません。
- tracerouteはOS間で頻度制限を揃えるため、TTL・試行ごとに単一UDPプローブを実行します。各応答は独立した観測であり、同一フローの経路を保証しません。
- HTTPS URLは認証情報・クエリ・フラグメントを許可しません。リダイレクト先のクエリ等も結果から除去します。
- 実機での確認状況は [検証記録](docs/validation.md) に記載します。IPv6インターネット接続成功やすべてのOS・ディストリビューションでの互換性を保証するものではありません。

[プロファイル例](examples/setup.json) は文書用IPを使ったダミーです。`local/` へコピーし、接続先を書き換えてください。[設定スキーマ](docs/schema/profile.schema.json) と [結果スキーマ](docs/schema/result.schema.json) を用意しています。追加キー、上限、結果データの意味は [チェック仕様](docs/checks.md) を参照してください。

配布は当面ソースからの `go build` とします。バイナリ配布とライセンスは未決定です。

## 公開リポジトリとしての運用

会場固有のSSID、パスワード、内部ネットワーク構成、端末情報、実測ログ、パケットキャプチャ、認証情報はコミットしません。サンプルにはダミー値を使用します。

[.gitignore](.gitignore) でローカル設定・秘密情報・診断結果を除外しています。ただし、除外設定は既に追跡されているファイルや文書内に貼り付けた情報には適用されません。公開前に差分を確認してください。

別の公開先へGitHub CLIで公開する場合の手順例です。`<owner>` は自分のアカウントまたは公開先Organizationに置き換えてください。

```sh
git status --short
git diff --cached
# 初回コミットがない場合は、確認した公開用ファイルを追加してコミットする
# GitHub CLIでログイン済みであることを確認したうえで実行
gh repo create <owner>/event-noc-check --public --source=. --remote=origin --push
```

現在の公開・リモート設定状況は `git remote -v` で確認できます。
